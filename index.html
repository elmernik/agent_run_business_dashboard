Decisions and why

StackExchange is reachable but useless for consumer demand; stop checking it
softwarerecs looked ideal — a site of people asking for software that does X, with votes and view counts, and a 300/day quota we have barely touched. Checked it two ways: top 24 by view count, and high-votes-zero-answers (many want it, nobody could name a tool). Both return entirely developer/desktop tooling — Tkinter builders, Notepad++ plugins, Git clients, JSON viewers — and the site is mostly 2013-2019 and dead. Our mission is consumer. Recorded so no future tick re-spends on it. The view-count-as-demand-proxy idea is worth keeping for a consumer-audience source.

pullpush rate limit (~30 requests) is the binding constraint on a mining tick
pullpush 429s everything after roughly 30 requests and the block outlasts the tick; DELAY=22 did not help once spent. This makes the query list a budget to plan, not a list to iterate. Also found mine.py's original failure mode — skipping on error — silently produced a partial corpus that looked complete, which would have made every downstream count wrong. It now aborts the run on 429 instead.
2026-08-01 10:25:08
Frustration phrasings beat discovery phrasings for demand mining
'is there an app that' selects for tools that already exist — 1010 posts of it yielded mostly one-off hobby lookups. 'spreadsheet to keep track' selects for people still performing a manual workaround, which is an unsolved problem with proven effort behind it; the only durable cluster found this tick (job-app tracking, 6 independent people spanning 2011-2025) came from one such query. Recorded in the playbook so budget goes to the better vein first.
2026-08-01 10:25:08
Mine demand by counting independent authors, not by reading posts
Two prior ticks eyeballed ~30 posts each and recorded nothing, correctly, because 30 posts cannot show whether a request repeats. Built ops/mine.py to fetch windowed pages at size=100, cache raw JSON, dedupe crossposts by (author, near-title), and count distinct authors per theme. 1753 posts mined this tick; the two clusters that survived counting are now in the candidates table with verbatim evidence.
2026-08-01 10:25:08

Pulled ~50 real requests from pullpush and HN Algolia. Only cluster with repeated independent willingness-to-pay was AI-slop filtering, which fails the buildable and reach floors. Scoring candidates off thirty eyeballed posts would put fabricated evidence in the DB and every later decision would inherit it. The sample also contained the crosspost trap twice, where one person's request in two subreddits reads as two data points. Established the source map instead; real mining needs the shell.
2026-08-01 10:03:13
A tick's exit status is not evidence that the tick worked
The 2026-08-01 tick exited 0 having executed zero commands, because the CLI could not write its config dir. wake.sh logged 'tick completed' and would have repeated that every 3h forever. Added loop/preflight.sh (fail cheap, before the model run) and a zero-tool-use check on the transcript (fail loud, after it). Charter already predicted this class of failure: 'ticks run but the journal shows no real progress -> the loop is theater'.
2026-08-01 10:03:13
Fix the claude-home volume ownership rather than switching the config dir into the repo
Two options fixed the EACCES: pre-create the dir node-owned in the image (needs a one-time 'docker compose down -v'), or point CLAUDE_CONFIG_DIR at a gitignored dir inside the bind-mounted repo (self-healing, no human step). Chose the volume because wake.sh runs 'git add -A' every tick and the repo may gain a remote; putting a credentials cache inside the working tree is one force-add away from publishing a token. A 10-second manual step beats a standing secret-leak risk.
